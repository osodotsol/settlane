# Security model and test acceptance criteria

Settlane is an unaudited hackathon prototype for simulated ETH only. Passing tests does not make it secure.

## Trust assumptions
- **Verifier.** Trusted to approve or reject honestly. It can wrongly reject (the client is refunded) or wrongly approve (the provider is paid). It cannot move funds or change parties. A provider and verifier controlled by one person behind two addresses defeats the system, and Settlane cannot detect this. The same attack is documented against ERC-8183.
- **Timestamp.** Block producers can skew it by a few seconds near a deadline.
- **Off-chain artifacts.** `spec` and `evidence` are commitments. Settlane does not check the content.

## Lost keys lock funds permanently (review S-3)
Settlane has no admin, owner, sweep, or recovery path, by design. The consequences:
- **Approved milestone, provider key lost.** `Approved` never expires and only the stored provider can `Claim`. The amount stays locked in the contract forever. The client cannot recover it, because refunding an approved milestone is forbidden (RA).
- **Expired milestone, client key lost.** Only the stored client can `Refund`. The amount stays locked forever. The provider cannot claim it, because it was never approved.
- **Client is a contract that cannot issue `Refund`.** A factory, a multisig without arbitrary calls, or any contract with no code path to call Settlane locks every refundable milestone it funds. Choosing `to` (RA) helps only if the client can make the call at all.
- **Provider or client is a contract that cannot receive a 2300-gas send.** This does not lock funds, because the caller picks `to` (D-004, D-005a).
These locked amounts stay in `outstanding`, so I1 and I9 still hold. Parties should use keys they control and can back up, and an EOA or a contract able to call `Claim`/`Refund`. The README must state this limitation.

## Invariants (each must have at least one test)
| ID | Invariant |
| --- | --- |
| I1 Conservation | Per agreement, `deposited == paid + refunded + outstanding` after every transition. |
| I2 Allocation | `deposited == Σ amount_i`, and every used milestone has `amount > 0`. |
| I3 Exclusive settlement | A milestone ends in exactly one of `Paid` or `Refunded`. Neither can be reached after the other. |
| I4 No double payment | A second `Claim` or `Refund` on a milestone reverts and leaves balances unchanged. |
| I5 Authorization | Only the provider can Submit or Claim, only the verifier can Approve or Reject, and only the client can Refund. Every other caller is rejected. |
| I6 No premature refund | `Refund` succeeds only when the milestone is `expired` (`docs/LIFECYCLE.md`), by the stored client, with `to != 0` and the amount read from storage (RA). |
| I7 Transfer honesty | A failed send leaves state and counters exactly as they were before the call. |
| I8 Isolation | Actions on agreement A never change agreement B's state, counters, or parties. |
| I9 Solvency | `selfbalance >= total_outstanding == Σ outstanding`. |
| I10 Race exclusivity | At every `now`, at most one of {Approve or Reject, Refund} is permitted for a `Submitted` milestone, and at most one of {Submit, Refund} for a `Funded` one. |
| I11 Balance-neutral verification | `Create`, `Submit`, `Approve`, and `Reject` never change `selfbalance`, except that `Create` adds exactly `msg.value`. Needed because the compiler cannot enforce read-only `call` in contract arms (FE_NOTES E7). Backed by CI lint rules `E-CALL`/`E-BODY`/`E-EFFECT`/`E-UNSAFE`: the privileged effects (`Call`, `Create`, `Super`, `Evm`, `RawStorage`, `RawOps`) may appear only in `Claim` and `Refund`, and `unsafe` not at all. A balance check cannot detect a raw storage write (review H3), so the lint is the guard for that. |
| I12 Production clock | In `Settlane`, time is only `ctx.timestamp()`. No setter, argument, storage, or admin path can alter it (PC). Backed by lint rules `C-CLOCK` and `C-ABI` plus a runtime test. |
| I13 Immutable deadlines | No function changes `deliver_by`, `decide_by`, or the review period after creation (DE). |

## Required test categories
- **Creation.** Zero amounts, n = 0 and n = 4, value ±1 wei, nonzero data in unused slots, sum overflow, zero parties, every pair among client, provider, and verifier equal (D-011), `deliver_by <= now`, zero review period.
- **Every row of the `docs/LIFECYCLE.md` table** with the authorized caller, one unauthorized caller (a third actor), and the boundary times d-1, d, and d+1, through rule tests and integration tests where time allows.
- **Every illegal (state, action) pair** reverts.
- **Repeats:** double claim, double refund, refund after claim, claim after refund.
- **Transfers:** a rejecting recipient (I7), `to == 0`, `to == ctx.address()` (review L-1), and a reentrant recipient that calls back into `Claim` or `Refund`.
- **Evidence and revision binding (D-015, D-021):** `Reject` and `Approve` with a mismatched evidence hash or submission revision revert and leave state unchanged.
- **Unset keys (D-017):** every action on an unused slot and on an unknown agreement id reverts.
- **Negative tests** use `evm.try_call(..).success()` after a positive control in the same test, then check state is unchanged. A bare `#[test(should_revert)]` passes on any revert, including one in the setup (review M2), so lint rule `T-REVERT` rejects it unless a `panic = ..` code names the reason.
- **Two agreements** interleaved (I8).
- **Invariant helper** after every step of the integration and demo tests.

## Phase 3A coverage (T5 Claim)
`Claim` is the only transition that moves ETH. `Refund` (T6) is **not implemented**, so I3 (exclusive settlement), I6, the refund half of I4 and I10, and "refund after claim" and "claim after refund" have nothing to test yet. They stay open for Phase 3B.

| --- | --- |
| I5 authorization | `only_the_provider_may_claim_and_only_an_approved_milestone_to_a_nonzero_payee`: the client (the test contract), the verifier and a stranger are each rejected **with the role reason** in the `Funded` and the `Approved` states, including when they name themselves or zero as the payee, with a positive control. `the_client_cannot_claim_and_a_claim_on_an_unknown_agreement_is_rejected` (production ingot) covers every slot. Pure order: `rules_claim_checks_run_in_the_documented_order`. |
| State guard (T5 row) | `Funded`, `Submitted`, rejected-back-to-`Funded`, `Paid`, unused slots 2 and 3 and unknown ids 0, 2 and 2^256-1 are each rejected with their own reason. `rules_claim_reports_each_failure_and_accepts_a_valid_claim` covers all six states. |
| I4 no double payment, replay | `the_provider_claims_an_approved_milestone_and_is_paid_the_stored_amount_once`: a second claim to the same or another payee is rejected (`milestone is not approved`), `Submit`, `Approve` and `Reject` after `Paid` are rejected, the milestone tuple never changes, and the payee's balance stays at one payout. |
| Amount and I1, I9 accounting | The same test: the payee receives exactly the stored amount, the call returns it, `paid` rises and `outstanding` falls by exactly that amount, `totalOutstanding` and the balance fall with it (`balance == outstanding`, no surplus here), the other milestones and a second agreement with the same parties are unchanged (I8), and after all three claims `paid == deposited` and nothing is outstanding. |
| I7 transfer honesty | `a_failed_transfer_reverts_the_whole_claim_and_a_retry_to_another_payee_succeeds`: payees that refuse ETH (an Actor without a fallback, the verifier's Actor, and **Settlane itself**, review L-1) make the claim revert with `transfer failed`. The milestone stays `Approved`, accounting and the balance are unchanged, the event is gone (the exact claim sequence in `check_events.py` has only the retry), and a retry to an EOA succeeds once. |
| Reentrancy | `a_reentrant_provider_is_paid_exactly_once`: the provider is a `Reentrant` contract whose payable fallback re-enters `Claim`. Under the stipend it receives exactly one payout and records **no** nested attempt. A second claim is rejected. A positive control sends it ETH with 500k gas: the fallback does try to claim again and the nested claim fails because the milestone is already `Paid`. The contract holds extra ETH from another agreement throughout, so a double payout would have been possible. |
| Non-payable | `claim_is_not_payable`, with a zero-value control. |
| No time guard, production vs shell | `approval_never_expires_and_production_and_the_shell_agree_on_claims`: the same verdict and reason on both contracts for each rejected claim, identical state after a claim, and the shell still pays an approved milestone 10^8 s after every deadline (positive control: `Submit` is closed then). |
| Events | `MilestoneClaimed(id, m, to, amount)` is decoded strictly by `scripts/check_events.py`. The replay allows a claim only of an `Approved` milestone, treats `Paid` as final, and checks that claims never exceed the agreement total. Six tests have their exact claim sequence checked, including which contract paid. |
| Code shape | Lint `C-STIPEND` (every production `send_value` passes `gas: 0`), `C-SEND` (its result is asserted in `assert!(..success()..)`) and `C-CEI` (no storage write or assignment after it in the same block). Test functions are exempt; a helper in a test file is not. |
| Mutation controls | 18 Phase 3A controls, each shown to make CI fail: anyone may claim, the verifier's role is checked, any state is claimable, a zero payee, state before role, not marked `Paid`, wrong amount, `paid` or `outstanding` not updated, the failed transfer ignored, gas forwarded, effects after the transfer (caught only by `C-CEI`, because the stipend hides it from the tests), effects after the transfer **with** gas forwarded (the reentrant provider is paid twice), payable, three event mistakes, and a reason with extra text. |
| Limits | The stipend and the ordering are two independent defenses, but `send_value(gas: 0)` means a payee that needs more than 2300 gas (some contract wallets) cannot be paid. The provider must pick another `to` (documented, D-004). The `std::evm::Mutex` guard is not used. The lint is textual. The verifier is trusted. |

## Phase 2A and 2B coverage (creation, funding, evidence submission, review, queries)
T1 to T4 exist. I3, I4, I6 and I7 are about payouts and refunds (T5, T6) and have nothing to test until Phase 3, and the refund half of I10 waits for the same reason. `Settlane` declares no `Call` effect at all, so the compiler guarantees it cannot send ETH in these phases.

The provider cannot approve its own work. |

| Immutability | `an_approved_milestone_stays_immutable_through_every_deadline`: after `Approved`, every action by the right role is rejected at six times, including after `deliver_by`, after `decide_by` and far in the future, and the milestone tuple is identical. ## Provisional-approval conditions (owner, 2026-11-18)
- **Refund authorization (RA), deadline enforcement (DE), and production clock (PC)** are specified in `docs/LIFECYCLE.md`. Each has named tests, and none may be weakened without a `docs/DECISIONS.md` entry.
- **CI must fail** when no tests run in either ingot or an ingot runs fewer tests than its floor (`scripts/check_tests.py`), when a non-payout arm or `init` lists or references a privileged effect (`Call`, `Create`, `Super`, `Evm`, `RawStorage`, `RawOps`, after normalising qualified paths and aliases), when a production contract declares an effect type the lint cannot classify (`E-EFFECT`) or production code contains `unsafe` (`E-UNSAFE`) or reuses a std effect name (`E-SHADOW`), when anything in the production ingot builds a `Clock` from anything but `ctx.timestamp()`, aliases or implements Clock, or binds `ctx` to anything but the Ctx effect (`C-CLOCK`), when the production ABI has a state-changing time or clock function or input (`C-ABI`), when the build output is not exactly the fresh deployable allowlist, counting every file in `out/` (`C-ARTIFACT`), when a test-only contract is defined in the production ingot or a deployable one in the dev ingot (`C-LAYOUT`), or when a test uses a bare `should_revert` (`T-REVERT`). That is `scripts/settlane_lint.py`, wired into `.github/workflows/ci.yml` and and since Phase 3A when a production `send_value` forwards gas (`C-STIPEND`), ignores its result (`C-SEND`) or is followed by a write (`C-CEI`). That is covered by 59 fixtures in `scripts/lint-fixtures/` and 45 unit checks. CI also re-runs every review repro (`experiments/review/run.sh`).
- **Proof that CI fails.** `python3 scripts/ci_negative_controls.py` copies the workspace, applies one deliberate mistake at a time (no tests in either ingot, dev ingot in `default-members`, a test shell in the production ingot, a production contract taking its time from a message argument, unformatted code, and since review 2026-11-18 one compiling shape for each of H1–H4 and M2), runs the real CI steps, and checks each fails at the expected step while an unmodified copy passes (91 mutations and 1 unmodified control as of Phase 3A). Run it after any change to CI, the lint, or the policy.
- **Limits of the lint.** It is a textual check, not a Fe parser. It cannot prove that the bytecode tested equals the bytecode shipped. It fails closed on empty or unparsable scans and on unclassifiable effect types, but a syntactic construct it does not recognise could slip through. Bypasses found and fixed so far: a payout arm name reused on another message type (fixed with `Msg::Arm` and `E-DUP`); a qualified or aliased `Call` type, a lowercase arm name, raw storage, and two `C-CLOCK` shapes (review 2026-11-18, `docs/reviews/2026-11-18-phase1.md`, each with a fixture and a negative control). Codex review (R-001), the I11 balance-neutral tests and the PC runtime test therefore remain necessary. Passing the lint does not make a contract secure.

## Reentrancy policy
Two independent defenses, both enforced: (1) checks, then every write, then `send_value`, then `assert!(success)` (lint `C-CEI`, `C-SEND`); (2) only the 2300-gas stipend is forwarded (`gas: 0`, lint `C-STIPEND`). The reentrant-recipient test exists since Phase 3A (`a_reentrant_provider_is_paid_exactly_once`), and the controls show each defense matters: forwarding gas alone lets the attacker try (caught by the test), and moving the writes after the transfer with gas forwarded pays it twice (caught by the test). The `std::evm::Mutex` guard is added only if a test or review shows the ordering is not enough. Refund (Phase 3B) must follow the same shape.

## Phase gate
A phase that touches payout, refund, or authorization is done only when the related invariants have passing tests and the `contract-security` checklist is clean, or its open items are recorded in `docs/PROGRESS.md`.
