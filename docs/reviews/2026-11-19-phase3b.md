## The eight points
1. **Authorization and exclusivity.** Only the client can refund, only a `Funded` or `Submitted` milestone. Only the provider can claim, only an `Approved` one. `Approved` is never refundable, `Paid` and `Refunded` are final. Checks run in LIFECYCLE order before any write. Verified in `rules::check_refund` and `rules::check_claim`, and by the tests that name each caller and each state.
2. **Exact amounts and recipients.** Both handlers bind `let amount = x.amount` and send it to the caller's `to`, which must be nonzero. `C-XFER-SOURCE` fixes that source and the tests check exact balances and return values.
3. **Deadline boundaries.** `rules::expired` is exactly the spec predicate: `Funded` at `deliver_by`, `Submitted` at `decide_by`, never for other states, on the milestone's own stored deadlines. Tested at d-1, d and d+1 in every slot, with different deadlines per slot, plus the rejection-after-`deliver_by` case (F3). Submit and Refund, and review and Refund, are disjoint at every second (pure test).
4. **Rollback.** A refused transfer reverts state, both counters and the event, and a retry to another payee succeeds once (tests, and the exact event sequences).
5. **Reentrancy.** Every write precedes a stipend-only send. Both no-threshold attackers fail as clients and as providers. See L-2 for the case that was not tested.
6. **G-1 and transfer restrictions.** `C-XFER-ARM`, `C-XFER-SOURCE` and the `C-XFER-RAW` extension close G-1 and the rebinding shapes. No lint bypass was found in the time spent.
7. **ABI, events, clock, coverage.** `refund(uint256,uint8,address)->(uint256)` (nonpayable) and `MilestoneRefunded` are in the ABI lock. The event checker rejects a double refund, a refund after a claim, a claim after a refund and payouts above the deposit. The production clock is the weak point: L-1.
8. **Accounting across agreements.** `check_invariants` runs after every refund step, including interleaved claims and refunds across two agreements with different clients.

## Findings

### L-1 (Low, gate coverage) — a frozen or shifted production clock in four of the five arms is invisible to every test and had no negative control
- **Evidence.** Freezing the clock at 0 in the production `Refund` arm, or in the `Submit` arm, left fmt, both checks, all 82 tests and the event checker green. Only lint `C-CLOCK` failed (plus `C-XFER-ARM` for Refund).
- **Why the controls missed it.** The only control for this, `mut-production-clock-frozen-at-zero`, replaces the first occurrence of `Clock { now: ctx.timestamp() }`, which is the `Create` arm. Nothing covered `Submit`, `Approve`, `Reject` or `Refund`.
- **Why the tests miss it.** The test block never advances and creation requires a future deadline, so no test can reach a successful refund on the production contract (D-024 item 7). A clock frozen at 0 is consistent with every production test.
- **Impact if it shipped.** A Refund clock stuck at 0 locks every unclaimed milestone forever. A Submit clock stuck at 0 keeps delivery open past `deliver_by`, so Submit and Refund would overlap.
- **Fix.** One negative control per arm, each required to be rejected by the lint with `C-CLOCK`. State in SECURITY that the production Refund arm's clock is checked only by the lint.

### L-2 (Low, coverage) — nothing tested a payee that re-enters the other payout
- **Evidence.** The existing attackers only re-enter the same payout on the same milestone. The probe in `experiments/review/r006/cross_*.fe.in` is a contract that is the client of one agreement and the provider of an approved milestone in another, whose fallback always claims the second.
- **Shipped code.** A refund to it reverts with `transfer failed` and nothing settles. With 500k gas its nested claim does land (the liveness control).
- **With gas forwarded in `refund_handler`.** The refund succeeds and the nested claim lands. Both settle exactly once and `check_invariants` holds, so write ordering alone keeps the books correct. The probe's first test fails, which is the stipend defense being enforced.
- **Fix.** Make the probe permanent, in both directions (refund payee re-entering Claim, claim payee re-entering Refund), each with a liveness control and rollback checks.

## Informational
- **Overclaiming comment.** The boundary test said the verifier "can still act" at `decide_by - 1`, but the test does not assert it. The Phase 2B review-window test does.
- **The lint checks presence, not value.** The required-writes check confirms each write exists before the send, not that its value is right. The tests cover the values (mutation "Refund also adds to `paid`").
- **Event checker limits.** It cannot check per-milestone amounts or deadlines from events, which is R-3 of R-005 again.
