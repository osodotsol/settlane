## Critical and High findings

### C1 · The payout form accepts an irreversible precompile destination

**Reproduction and actual result.** `checkAddress("0x0000000000000000000000000000000000000004")` accepts the identity precompile. The existing Fe regression `precompile_payees_are_the_providers_own_choice_and_some_strand_the_eth` passed independently. A provider claims 1 ETH to `0x04`, the claim succeeds, and the ETH sits at that address. The same test pays `0x02`. The milestone is settled and cannot be claimed again. The refund handler uses the same stipend transfer, so the corresponding refund loss path follows from the shared transfer behavior. Severity reflects permanent loss after an authorized signature. This is a documented contract behavior and a frontend safety gap.

**Expected and fix.** The frontend should reject known chain precompiles as payout destinations before simulation, in both the payout form and the write runner. Apply the chain-specific checks to participant inputs where a protocol address cannot perform the role. Keep general EIP-55 validation and verify normal externally owned and eligible contract recipients with positive controls. [Address validation](../../frontend/src/domain/address.ts#L13) · [Payout UI](../../frontend/src/ui/app/MilestoneActions.tsx#L48) · [Fe reproduction](../../ingots/settlane-dev/src/tests.fe#L2944)

### H1 · Two tabs can start the same create before either observes the other's record

**Reproduction and actual result.** Load the same account in tabs A and B before either starts. Delay storage-event delivery while both request creation. Two registry instances accepted `checking` and `awaiting` for the same key while only A's Web Lock callback ran. B's lock was queued. `startTx` calls the wallet after updating the registry, without waiting for lock ownership. Whole-map localStorage writes can also replace a record written by the other tab, including records with different account keys. If the wallet presents both requests and the client accepts them, each valid payable `create` funds its own agreement. The registry race was reproduced offline. Wallet queue behavior and duplicate funding were inferred from that path and the contract's create semantics.

**Expected and fix.** Acquire the exclusive per-key Web Lock before admission, re-read durable state under the lock, and hold it through the wallet handoff and durable outcome update. Persist separate per-key records or transact updates so unrelated keys survive concurrent writes. When atomic admission or durable storage is unavailable, fail closed for create with actionable UI. Add a two-tab barrier test that verifies exactly one prompt reaches the injected provider. [Admission](../../frontend/src/chain/write.ts#L125) · [Storage and locks](../../frontend/src/chain/tx-registry.ts#L237)

### H2 · A different create with identical terms can clear an unanswered funding request

**Reproduction and actual result.** Leave create A unanswered and reload, then make create B from the same account on another device using the same absolute deadlines, amounts, parties and spec. Supply the B agreement to the mocked RPC. Recovery yields `found`, marks the draft eligible for clearing and allows another create. A remains unresolved and can still fund another agreement if approved before the deadline. A second probe gave A its own pending hash and supplied a mined identical call with a different hash. The reducer returned `confirmed` for the other transaction before examining A's pending status or the other tab's lock. Matching terms or calldata identifies an operation's contents. Wallet request identity is a separate fact.

**Expected and fix.** When an original hash exists, reconcile that hash or a verified replacement from the same sender and nonce. Check the transaction destination, calldata and value, and the canonical receipt and expected contract event before marking success. For a hashless payable create, keep the hold when a matching agreement or mined call is the only evidence. Show the matching agreement separately. Release only on demonstrable request closure or proof the recorded call is permanently invalid, such as finalized time past a used delivery deadline. A strong guarantee across independent devices requires an on-chain idempotency key in a future contract design. [Agreement matching](../../frontend/src/chain/tx-effect.ts#L56) · [Recovery priority](../../frontend/src/chain/tx-recovery.ts#L72) · [Draft clearing](../../frontend/src/ui/app/CreateSubmit.tsx#L23)

### H3 · Dismiss and legacy migration bypass payout and review intent protection

**Reproduction and actual result.** Lose a `claim` to A, use the milestone attestation, and try a claim to B. The first attempt to B is correctly blocked. Dismiss that failure and try B again. The wallet mock receives the B call while the earlier A call remains unresolved. The same delete path serves other terminal panels, so it can discard older review and submit records too. A separate probe loaded an unresolved pre-R2-C claim with no saved calldata. Attestation unlocked a different payee because the original call could not be copied into the earlier-request list. Either payout could win. T5 and T6 still permit only one payout, and a stale alternate would revert.

**Expected and fix.** Make dismiss hide only the displayed status. Retain unresolved requests with stable unique IDs separately from the latest attempt. Keep legacy records with unknown calldata conservative. Allow release only on request-specific proof or finalized proof that any possible legacy call is permanently ineligible. Test the complete sequence through Dismiss, reload and alternate payee or decision. [Earlier-request construction](../../frontend/src/chain/write.ts#L132) · [Dismiss](../../frontend/src/chain/write.ts#L396) · [Result UI](../../frontend/src/ui/app/TxPanel.tsx#L169)

### H4 · An identical submit retry can erase the old request and bypass later consent

**Reproduction and actual result.** Lose an unanswered submit for evidence `0x11`, attest and retry `0x11`. Let the retry mine at account nonce 5. The app then starts a submit for `0x22` without consent. `liveGhosts` finds the retry's identical calldata in the old request's nonce scan and removes the old request. A late `0x11` can still replace `0x22` before `deliver_by`, and the data for the late-replacement alert has been discarded. Any approval naming the superseded revision then reverts. The wallet admission and removed warning data were reproduced with mocks. The late overwrite and revision check follow T2–T4 and are covered by the Fe lifecycle and existing browser scenarios.

**Expected and fix.** Keep the older request until its own hash or a proven same-nonce replacement resolves, or finalized contract state makes it unexecutable. Exclude a known retry's hash from any proof about an earlier request. Bind consent to the current evidence hash and exact set of unresolved requests. Retain the latest successful evidence and unresolved submission history across dismissal and reload. [Pruning](../../frontend/src/chain/write.ts#L96) · [Evidence warning](../../frontend/src/ui/app/MilestoneActions.tsx#L58) · [Lifecycle](../LIFECYCLE.md#implementation-notes-phase-2b-t2-to-t4)

## Settlement, wallet and deployment observations

- Fe T1–T6 all have passing rule or integration coverage. The in-process VM verified exact funding, evidence and revision binding, strict deadlines on the test clock, payout authorization, terminal exclusivity, repeated payouts, payout rollback, cross-agreement balances and reentrancy. I found no new way to bypass these guards. Payouts to contracts that cannot receive the stipend revert and can be retried with a usable payee.
- Account-scoped records, explicit `account` in the simulated request, and wallet chain checks are present. Existing wallet-mock coverage passed. A transaction already in the wallet may still follow the wallet's approval flow after an account or chain change. Revalidate the active account and chain immediately before dispatch. Confirm actual sender, chain, destination and calldata during reconciliation.
- Simulate and estimate happen before opening the wallet. A submission, review or create can expire while the wallet waits. The Fe guards protect escrow at inclusion. A revert can still cost gas, particularly with the supplied gas limit suppressing a fresh wallet estimate. Refresh the simulation and block clock immediately before handing off, display remaining time while waiting, and instruct the user to reject an expired request. An already-presented request can only be managed in the wallet.
- `latest` reads across independent fallbacks and the first receipt lack a common finalized block. Require canonical and finalized evidence before irreversible recovery decisions, pin comparable observations to a block, and report provisional confirmation separately. Validate RPC chain ID and expected runtime on the write-enabled deployment. Existing configuration assumes Sepolia while allowing alternate RPC URLs and addresses for test runs. The read-only deployment checks below exercise the default configuration.

## Verification results

Test evidence added 2026-11-24 from the final independent review and its fixes (`docs/reviews/2026-11-24-final-independent-review.md`). Mock wallets and the Anvil stand-in wallet only; no real MetaMask run.

- **Fe gate** at `deefab5`: format, both checks, 90 tests (43 + 47), event checker, build, policy lint and the three self-tests all passed. The fresh build equals the pinned artifact (`testnet.py artifact`).
- **Frontend at `deefab5`:** ABI check, lint, typecheck passed; 203 unit tests passed, 2 skipped (the opt-in live Sepolia file is skipped, not counted). Browser: Sepolia read-only 25/25, Anvil 5/5, simulated-wallet app 24/24, hanging RPC 3/3. `npm audit --omit=dev`: 0 vulnerabilities.
- **After the fixes (M1, H3, H4, M3):** 216 unit tests passed, 2 skipped; lint, typecheck and production build passed. Browser, Anvil 5/5 and hanging RPC 3/3 passed. Simulated-wallet app: 24/24 on the rerun; in the first run one test timed out (a "Check the chain" button kept detaching, not reproduced on the rerun, cause not found). **Sepolia read-only: 24/25 in both runs.** The failing test calls `networkEvents()` in the test process, which reads logs from the public node, and the node answered "pruned history unavailable" for a recent range (it had passed 25/25 the same day before). The application part of that test passed. The rest of that test, the Activity page's count and filter, was not exercised, and it counts as a failure, not a pass.
- **Not run:** real MetaMask, `ci_negative_controls.py`, `experiments/anvil/run.py`, the Sepolia rehearsal.

The write frontend remains blocked on C1 and H1–H4. Resolve M1 and M2 as part of the same recovery changes. Before reopening writes, run the browser write suite against an authorized disposable environment and repeat the affected cases with real MetaMask. For a release claiming complete history or broad RPC outage tolerance, close M3–M7 or narrow the applicable claims and publish the test evidence. The Fe code and ABI need no change for the immediate frontend corrections. The audited scope ends here pending implementation approval.
