# R-005 — Phase 3A security review (Claim)

- Commit reviewed: `b3a12f1` on `settlane/dev`, Fe 26.6.0 (5b3f96a), 2026-11-19.
- Reviewer: Claude (not Codex). This is not the Codex R-005 assignment in `docs/HANDOFF.md`, which is still not run. No production code was changed. All probes ran in temporary workspace copies.
- Evidence: `experiments/review/r005/` (see "Saved evidence" at the end). Run `bash experiments/review/r005/run.sh` from the repo root; exit 0 means every reproduction still behaves as recorded here.

## Verdict
- **The shipped Claim code is correct for every property checked.** Authorization, state guard, payee check, amount from storage, ordering, stipend, revert on failure, accounting, event, and non-payable all hold. I found no exploitable defect in the `b3a12f1` bytecode.
- **The gate that is meant to keep it correct has a confirmed hole (F-1, High).** A compiling `claim_handler` that pays a 1 ETH milestone twice, out of another agreement's escrow, passes the full CI gate: fmt, check, 66 tests, events, build, and policy lint.
- **Phase 3A: acceptable as code, conditionally.** Fix or explicitly accept F-1 before the phase is closed. Owner approval of D-022 is still pending.
- **Phase 3B: do not start until F-1 is fixed** and the decisions in "Phase 3B readiness" are made. Refund adds a second transfer site, and the current lint would not catch the same regression there.

## Confirmed defects

### F-1 (High, gate/CI) — The transfer lint and the reentrancy test can both be bypassed. A double-payout claim passes the whole gate.
- **Location:**
  - `scripts/settlane_lint.py:403-434` (`transfer_rules`: C-STIPEND, C-SEND, C-CEI).
  - `ingots/settlane-dev/src/lib.fe` `Reentrant` fallback (`lib.fe:277`, `if ctx.gas() < 60000 { return }`).
  - `ingots/settlane-dev/src/tests.fe:2369` `a_reentrant_provider_is_paid_exactly_once`.
- **Mechanism:**
  - C-STIPEND accepts any `gas:` argument that matches `gas\s*:\s*0\b`, so `gas: 0 + 57000` passes.
  - C-CEI only scans the rest of the block that contains the `send_value`. A send inside `if .. { }`, followed by writes, passes.
  - The only test that can see forwarded gas uses an attacker that refuses to re-enter below 60,000 gas. 57,000 forwarded plus the 2,300 stipend stays under that threshold.
- **Reproduction** (`experiments/review/r005/patches/b7_double_pay_under_60k.patch`): `claim_handler` sends first, inside `if amount > Wei::zero() { assert!(call.send_value(addr: to, gas: 0 + 57000, value: amount).success(), "transfer failed") }`, then writes `Paid`, `paid` and `outstanding`. Results:
  - `fe fmt --check ingots`: 0.
  - `fe check` for both ingots: 0.
  - `check_tests.py`: ok, 66 tests.
  - `check_events.py`: ok.
  - `fe build` plus `settlane_lint.py ingots --abi-dir out`: ok.
  - A re-enter-once attacker (`Once`, in `experiments/review/r005/dev_lib_additions.fe.in`), against a 1 ETH milestone with 9 ETH in escrow across two agreements: the test `r005_b7_once_is_paid_twice` passes. The attacker holds 2 ETH, the contract 7 ETH, and `totalOutstanding` is 7 ETH. Agreement 1 still records `paid = 1` and owes 2 ETH (stale write), and agreement 2 owes 6 ETH. So 8 ETH is owed against 7 ETH held: I1 and I9 are broken, and agreement 2's funds paid the attacker.
  - Control: against the unmodified `b3a12f1` code, the same attacker is not paid at all. Under the stipend its fallback cannot store its flag, so the send fails and the claim reverts with `transfer failed`.
- **Related bypasses** (lint passes in every case). The ones the tests also miss are CEI breaks that cannot be seen under the stipend:

  | Shape | Lint | Tests |
  | --- | --- | --- |
  | b1 `gas: 0 + 100000` | pass | caught (reentrancy test) |
  | b2 `call.try_call_raw(.., gas: 100000, ..)` instead of `send_value` (no transfer rule applies) | pass | caught |
  | b2b `try_call_raw(gas: 0)` + write after | pass | **pass** |
  | b3 send in nested block + write after | pass | **pass** |
  | b4 send in a helper `pay()` called before every write | pass | **pass** |
  | b5 `.success() \|\| true` | pass | caught (failed-transfer tests) |
  | b6 `#[test]` on a production helper that a contract calls | pass (exempt); `fe check` and `fe build` accept the call | caught incidentally: the dev tests fail because the helper ignores the result, and `fe test` of the production ingot crashes in the Fe Sonatina backend (`synthetic owner-effect arg count mismatch`, a compiler panic, not a test failure) |

  Also, `Call` exposes `raw_call`, `try_call`, `call`, `raw_delegatecall` and `delegate` to any code holding `mut call`, and none of these are checked.
- **Impact:** none on the current bytecode. But SECURITY.md "Reentrancy policy" says both defenses are "enforced", and they are not: (1) ordering is enforced only for one textual shape, and (2) the stipend is enforced only above ~57.7k forwarded gas, by the test. A regression in Claim, or the same mistake in Refund, can ship green. The negative controls test only one exact text shape (`gas: 500000`, same-block reordering), so they cannot show this.
- **Minimal fix (both parts):**
  1. **Lint, fail closed on shape.** In the production ingot, allow exactly one transfer form: the literal `assert!(call.send_value(addr: to, gas: 0, value: amount).success(), "transfer failed")` as the last statement before the return value of `claim_handler` (and, later, `refund_handler`), at function-body depth 1. Reject any other method on a `Call` binding (`raw_call`, `try_call*`, `call`, `delegate*`, `call_with_*`) in production. Require the `gas:` value to be exactly the token `0` (followed by `,` or `)`). Remove the `#[test]` exemption in the production ingot (production has no test that sends). Add b1–b7 as fixtures and negative controls.
  2. **Test.** Give `Reentrant` no gas threshold for the attempt decision. Record the attempt in a way that works under the stipend, or (simpler) add a second attacker like `Once` that re-enters exactly once with whatever gas it gets. Then assert that a claim to it under the stipend fails with `transfer failed` or pays exactly once. Add a negative control with forwarded gas below 60k (for example `gas: 50000` with effects after the transfer) that must make this test fail.

### F-2 (Low, tests) — The reentrancy test's "no nested attempt under the stipend" is vacuous
- **Location:** `ingots/settlane-dev/src/lib.fe` `Reentrant` `_` arm (`lib.fe:277`), and `tests.fe:2422-2425`. The claim appears in `docs/SECURITY.md` ("Reentrancy" row) and `docs/FE_NOTES.md:173` ("the attacker cannot even attempt a nested call").
- **Evidence:** the fallback returns before trying whenever `ctx.gas() < 60000`, so `stats == (0, 0)` reflects the attacker's choice, not the stipend. My `Greedy` probe always re-enters: under the stipend, the nested attempt makes the fallback run out of gas, and the claim reverts with `transfer failed` (`r005_greedy_provider_always_reenters` passes). The stipend therefore does block the nested payout, but the existing test does not show it.
- **Fix:** the test part of F-1 covers it. Reword the docs: under the stipend, a re-entering payee cannot be paid twice and its claim fails. The attacker "cannot even attempt" is not what was measured.

### F-3 (Low, tests/policy) — Non-payable claim negative test asserts only failure
- **Location:** `ingots/settlane-dev/src/tests.fe:2491` (`claim_is_not_payable`, `assert!(!out.success())`). The same pattern is in `transitions_are_not_payable_and_never_move_money`.
- **Evidence:** CLAUDE.md says every negative test asserts its revert reason. My probe `r005_nonpayable_claim_returns_empty_revert_data` shows that Fe's non-payable revert has empty returndata, both directly and when re-raised by the Actor. An empty-data assertion would separate it from every reasoned revert (`milestone is not approved` and so on).
- **Fix:** also assert `out.returndata_len() == 0`, or add a `Why::NonPayable` that matches empty data in `because`.

### F-4 (Low, docs/comments) — Stale "cannot send ETH" statements
- **Location:**
  - `ingots/settlane/src/lib.fe:11-13`: "Phase 2A … this contract has no `Call` effect, so it cannot send ETH at all".
  - `ingots/settlane/src/handlers.fe:5-6`: "No handler here lists `call` … the contract does not even declare those effects".
  - `handlers.fe:256`: "claimed in a later phase".
  - `docs/LIFECYCLE.md:42`: "`Settlane` still declares no `Call` effect, so the compiler guarantees it cannot send ETH".
- **Impact:** these are false since `b3a12f1`. They misstate the one compile-time guarantee left: omission per arm, not per contract. Reviewers and judges rely on these lines.
- **Fix:** say that `Settlane` declares `Call`, that only the `Claim` arm lists it, and that the other arms omit it (compiler-enforced, `8-0012`/`8-0036`; probes e7b and e7c), backed by E-CALL and E-BODY.

### F-5 (Low, tests) — The full invariant helper never runs after a successful claim
- **Location:** `check_invariants` exists only in `ingots/settlane/src/tests.fe:169`. The production ingot cannot produce an `Approved` milestone (it has no Actor), and the dev claim tests use `assert_money` plus spot `accounting` tuples.
- **Impact:** SECURITY.md says "Invariant helper after every step of the integration and demo tests". For claims, "per-agreement outstanding == Σ live milestone amounts" and "totalOutstanding == Σ outstanding" over all agreements are checked only indirectly. The b7 corruption above (8 ETH owed, 7 ETH held) would be caught immediately by that helper.
- **Fix:** move or copy `check_invariants` into the dev ingot and call it after every claim step.

## Untested risks and observations (not defects)
- **R-1 Precompile payees.** `to = 0x02` (sha256) or `0x04` (identity) succeeds, and the ETH is stranded forever. `to = 0x01` (ecrecover, 3,000 gas) fails with `transfer failed` (probe `r005_precompile_payees`). This is the provider's own choice of `to`, so it is informational. Optionally document it.
- **R-2 Liveness.** A payee that needs more than 2,300 gas, or that re-enters, can never be paid (its claim always reverts). The provider can always choose an EOA, as documented in D-004. A provider that is a contract without a code path to call `Claim` locks the milestone forever, as documented in S-3.
- **R-3 Event stream limits.** `check_events.py` replays claims against the agreement total only. `AgreementCreated` carries no per-milestone amounts, so an indexer cannot check a claim's amount from events alone. Exact amounts are checked in 6 named tests.
- **R-4 Latent payout permission.** `scripts/lint-policy.json` already lists `SettleMsg::Refund` as a payout arm, so any arm added with that name gets `call` permission without a policy change. This is intended for Phase 3B; it is noted so 3B's review checks it.
- **R-5 E7 is still live on 26.6.0.** Phase 1 `run.sh`: `e7_fail_readonly_call` and `e7/b,c,i,j` compile, and `j_runtime` moves 1 ETH. On the real contract, `Submit` listing `call` read-only compiles (probe e7a, `fe check` 0) and is rejected only by lint E-CALL. If `call` is omitted, the compiler rejects both direct use and calling `claim_handler` (e7b, e7c: `8-0036 missing effect Call`).
- **R-6 Read-only reentrancy.** During the payee callback, views already show `Paid` and the reduced counters, and the ETH has already moved (value moves before callee code runs). The views are consistent, and no external protocol reads them.

## Checklist by area
1. **Authorization.** Provider only, `Approved` only, `to != 0`, amount from storage (`x.amount`, not calldata). Unknown ids (0, 2, 2^256-1), unused slots (2, 3), wrong roles and replays are rejected with exact reasons. Verified in code (`rules.fe:257-280`, `handlers.fe:380-449`) and in tests.
2. **State and accounting.** `Paid`, `paid += amount` and `outstanding -= amount` are written before the send. `paid + amount <= deposited` and `outstanding >= amount` hold by construction, and arithmetic is checked (E8). Zero amounts are impossible (`amount > 0` at creation, so the stipend always applies). A second claim reports `milestone is not approved`.
3. **ETH transfer.** The stipend is at most 2,300 gas: probe `r005_payee_gets_at_most_the_2300_stipend`, with a control showing the same payee rejects 10,000 gas. A failed send reverts state, counters and the event (tests plus `check_events`). A payee of Settlane itself fails.
4. **Fe effects.** Only `Claim` lists `call` (lint ok). E7 is reproduced. Omission is enforced, including through the shared handler. The lint gaps are in F-1.
5. **ABI and events.** `claim(uint256,uint8,address)->(uint256)` is nonpayable and locked. `MilestoneClaimed(uint256 indexed,uint8 indexed,address indexed,uint256)` is locked and emitted once per success, with none on failure.
6. **Tests and CI.** The full gate passes on `b3a12f1`: 66 tests (39 + 27), events, build, lint, all three self-tests, and review repros. Negative controls: **92/92 ok, 0 WRONG**, including the unmodified control (CI PASSED) and all 18 Phase 3A controls (full run, exit 0); `--dry-run` 92/92 apply. Phase 1 experiments: exit 0, every acceptance is a known E7 gap. Controls check the failing CI step, and only `ONLY_FAILING` entries pin the failing test. None covers forwarded gas below 60k, or the CEI shapes b2b, b3 and b4.
7. **Phase 3B readiness.** See below.

## Phase 3B readiness
- **Exclusivity.** Claim accepts only `Approved`, and the planned Refund accepts only `Funded` or `Submitted` plus `expired`. `Approved` has no other exit, and `Paid` and `Refunded` are both rejected by `check_claim` (rules test covers `Refunded`). Paid and Refunded are exclusive by the state machine. I3, I4 (refund half), I6 and I10 (refund half) still have no tests.
- **Accounting.** Refund must mirror Claim: `refunded += amount` and `outstanding -= amount` before the send, with the amount from storage. Both share `totals.outstanding`. Under CEI, cross-function reentrancy (a payee calling Refund or Claim on another milestone during the callback) sees committed state, which is safe.
- **Decisions needed before Refund:**
  1. Fix F-1 first, with a lint rule shape that names both payout handlers. Otherwise a shared `pay()` helper, the natural way to deduplicate Claim and Refund, is already invisible to C-CEI (b4).
  2. Owner approval of D-022. Resolve D-005: its row still reads "open", while D-005a is provisionally approved.
  3. Refund check order and reasons: agreement, client role, milestone exists, state ∈ {Funded, Submitted} (reason for `Approved`/`Paid`/`Refunded`), `expired`, `to != 0`. Decide whether `expired` precedes `to != 0`, as window precedes evidence elsewhere.
  4. `refund(uint256,uint8,address)->(uint256)`, nonpayable, with `MilestoneRefunded(id indexed, m indexed, to indexed, amount)`, added to the ABI lock in the same change.
  5. Whether to add the `std::evm::Mutex` guard once two send sites exist. Not required under correct CEI, but it is cheap insurance against F-1-style regressions.
  6. The Refund reentrancy test must not inherit the 60k threshold (F-2).
